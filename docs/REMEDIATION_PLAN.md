## 4. A02: сохранение и безопасная смена проекта

### 4.1. Контракт очереди

В `src/core/persistence.ts` добавить ожидание сохранения конкретного снимка, например `flush(snapshot): Promise<SaveReceipt>`. Квитанция содержит id проекта, contentRevision и storageRevision.

- `flush` немедленно подаёт последнюю сцену в очередь, не ждёт 250-миллисекундного debounce.
- Если старая запись уже выполняется, она завершается первой, затем сохраняется актуальный снимок. Записи не запускаются параллельно внутри одной очереди.
- Подтверждение старой revision не удовлетворяет ожидание новой. Последние pending-правки можно объединять, но нельзя терять ожидающих подтверждения.
- Сохраняется CAS: read/compare/write внутри одной IndexedDB-транзакции. Конфликт не превращается в принудительное перезаписывание.
- Отказ завершает ожидание понятной ошибкой. После отказа нет вечного «Сохраняем…» и необработанного rejected promise.
- Закрытие редактора разрешается только после безопасного завершения перехода. Простое `close()` больше не используется как способ отбросить ещё нужный снимок.

### 4.2. Единый путь перехода

Создание новой сцены, открытие файла и выбор сохранённого проекта проходят через один контроллер переходов.

1. Файл назначения сначала прочитать и проверить целиком. Повреждённый файл не должен закрывать рабочий проект.
2. Завершить редактирование названия. Незавершённый drag-preview отменить; источником снимка является подтверждённая модель сцены.
3. Зафиксировать снимок текущего проекта и токен перехода. На короткое время записи блокировать повторный переход и правки, которые сделали бы снимок неоднозначным. Экспорт текущего снимка остаётся доступен при отказе.
4. Вызвать `flush` и дождаться подтверждения именно этого проекта/revision.
5. Только после успеха отменить старые задачи, закрыть старую очередь, открыть новый редактор и привязать к нему собственную очередь.
6. Поздние callbacks проверяют id проекта, revision и токен редактора. Совпадения одного числа revision недостаточно.

Двойное нажатие «Новая композиция» создаёт один переход. Параллельное чтение файлов по-прежнему использует правило актуального запроса. Повторная команда в уже начавшемся переходе не открывает второй проект скрыто.

Ожидание не должно блокировать UI бессрочно: рабочий предел ожидания перехода — 5 секунд. По истечении сцена остаётся открытой, доступны отмена и JSON. Таймаут ожидания **не считается отменой уже начатой IndexedDB-транзакции**; её поздний результат обрабатывается корректно, повторная параллельная запись не запускается.

### 4.3. Отказ, конфликт и отдельная копия

- При ошибке/квоте/блокировке базы обычный переход не выполняется. Сцена остаётся в памяти. Есть «Остаться», «Скачать проект» и явное «Продолжить без сохранения». По умолчанию остаёмся в редакторе.
- Нажатие скачивания само по себе не закрывает проект: браузер не даёт надёжного подтверждения, что пользователь сохранил файл на диск.
- «Сохранить отдельно» при CAS-конфликте не пытается сначала записать конфликтующую исходную запись. Создаётся полный снимок с новым id; копия сохраняется с expectedRevision=0, и только после успеха открывается. При ошибке исходная версия в памяти сохраняется.
- «Открыть актуальную» после конфликта — отдельный явный отказ от своей версии либо предварительное сохранение копии. Не маскировать потерю своей ветки автоматическим reload.
- Повтор после временного отказа использует прежнюю ожидаемую storageRevision. Нельзя автоматически принимать чужую новую revision за свою.

### 4.4. Доступ к уже сохранённой работе

Добавить в существующее меню проекта пункт «Открыть сохранённый проект»: небольшой прокручиваемый список названий и дат. Используются уже существующие записи IndexedDB. Без галереи, миниатюр, облака, папок и новой системы версий.

Открытие старого проекта не создаёт его дубликат и не выполняет лишнюю content-запись. Выбор активного id запоминается для этой вкладки в `sessionStorage`, чтобы reload возвращал выбранный проект, а не произвольную последнюю запись другой вкладки. Если указатель недоступен/повреждён/ссылается на отсутствующий id, используется безопасный fallback к существующей записи; данные не стираются. Недоступность запоминания выбора не объявляется успешной гарантией восстановления активного проекта.

Формат JSON и схема таблицы documents остаются прежними. Перед любым необходимым отклонением от этого решения отдельно описывается миграция с проверкой старой базы; автоматический reset запрещён.

Файлы: `persistence.ts`, `App.tsx`, компактный компонент выбора проекта в существующей структуре панелей. Тесты: D01–D18 в матрице.

## 5. A01: масштаб и пригодность композиции

### 5.1. Алгоритм

1. Рассчитывать размеры фактических вариантов выбранного набора: viewBox × sourceScale, с учётом поворота и роли. Не использовать первый небольшой объект как единственную меру всей сцены.
2. Выбирать начальный **общий** масштаб по всему набору главных предметов и доступному формату.
3. Для каждого из трёх существующих шаблонов ограниченно проверять положения, углы и несколько общих масштабов. Предлагаемый верхний предел — 120 кандидатов на запрос; бесконечный случайный поиск запрещён.
4. Разделить условия пригодности и эстетическую оценку. Сильный выход главного предмета за край или его полное перекрытие не компенсируется высоким баллом другого свойства.
5. Порядок слоёв выбирать так, чтобы небольшой значимый предмет не исчезал за большим. Не менять состав набора, не удалять неудобные объекты и не переводить главный объект в фоновый только ради прохождения проверки.
6. Предусмотреть детерминированную запасную раскладку с общим масштабом для допустимых 1–6 объектов, если художественный шаблон не прошёл ограничения. Она должна сохранять весь выбранный набор. Если доступны только один-два пригодных результата, показывать их честно, без трёх одинаковых копий и без заведомо плохих карточек.
7. Для одного и того же seed воспроизводится одна и та же геометрия/состав/порядок, без требования одинаковых случайных instanceId.

Карточка получает название из фактического варианта, а не из его индекса в старом массиве из трёх элементов. Запасной результат обозначается нейтрально, без обещания диагональной раскладки, если её в нём нет. Это не требует изменения формата сохранённых сцен.

Ручное добавление: если новый крупный объект при текущем масштабе получается заведомо чрезмерным, уменьшить **общий** масштаб сцены до пригодного значения; сохранить положения, углы и слои прежних экземпляров. Не увеличивать сцену автоматически при каждом добавлении. Изменение масштаба и добавление составляют одну Undo-команду. Ручное перемещение за край не ограничивать новыми правилами автоматической композиции.

### 5.2. Проверяемое качество

Для трёх стандартных форматов принимаем внутренние пороги автоматической сборки:

| Измерение                                                                                        | Минимум |
| ------------------------------------------------------------------------------------------------ | ------: |
| Доля исходного рисунка главного предмета, попавшая внутрь холста до перекрытий                   |     60% |
| То же для назначенного основного акцента, если шаблон его выделяет                               |     80% |
| Доля исходного рисунка главного предмета, реально оставшаяся видимой после вышележащих предметов |     35% |
| То же для основного акцента                                                                      |     55% |
| Доля добавленного фонового предмета внутри холста                                                |     10% |

Это наши критерии качества, а не численные требования работодателя. Их нельзя выдавать за текст ТЗ. Основным акцентом считается явно выбранный алгоритмом main, не обязательно первый введённый маленький объект.

Доли измеряет независимый тест по alpha-маскам реально отрисованных оригинальных SVG с учётом обрезки и перекрытий. Прямоугольник ограничений используется как дешёвый предварительный барьер, но не объявляется площадью рисунка. Прозрачные поля и пересекающиеся пустые углы не должны давать ложный вывод о полном перекрытии.

Численные пороги дополняются ручной оценкой: предметы узнаваемы, композиция не превращается в несколько увеличенных фрагментов, остаётся понятный акцент, результат соответствует стилю примеров. Тест не доказывает красоту автоматически.

Для экстремальных пользовательских форматов 128×4096 / 4096×128 обязательны валидная конечная геометрия, сохранение состава и пропорций, ограниченное время и отсутствие ошибок. Нельзя обещать одинаковую читаемость всех шести объектов в узкой полосе. Такие состояния проверяются отдельно и не подмешиваются к проценту хороших стандартных композиций.

Файлы: `composition.ts`, общая функция вычисления габаритов при необходимости, `commands.ts`, отображение фактически доступных кандидатов. Тесты: C01–C16.

Само добавление boundary не заменяет раннюю проверку ссылок.

### 6.2. Политика названия и экспорта

При импорте и проверке сохранённого проекта **отклонять** недопустимые XML 1.0 символы имени, включая запрещённые управляющие символы, U+FFFE/U+FFFF и непарные UTF-16 surrogate. Не удалять их молча из чужого файла. Корректные кириллица, emoji, кавычки и амперсанд сохраняются.

На границе экспорта — повторная защита: нельзя скачать файл, который не разбирается как SVG/XML. При нарушении инварианта — понятный отказ, сцена остаётся доступной, исходники не меняются. Нельзя превращать U+0000 в `&#0;`: это также недопустимый XML.

Обычный ввод названия использует локальный черновик; подтверждение по Enter/blur одной командой. Пустой черновик разрешён во время набора. При подтверждении пустого имени применяется понятное название по умолчанию; Escape возвращает прежнее значение. Ввод запрещённого символа не создаёт ошибочный документ. Неподтверждённый изменённый черновик учитывается предупреждением при закрытии страницы и не объявляется сохранённым; внутренний переход сначала подтверждает или явно отменяет его.

Файлы: `svg.ts`, `catalog.ts`, `validation.ts`, `App.tsx` / небольшой error boundary. Тесты: S01–S16, N01–N08.

## 7. A03 и ясность интерфейса

### 7.1. Холст

Использовать фактическую свободную область, измеренную ResizeObserver. Отступы, подпись и панели учитываются один раз. Убрать двойное вычитание фиксированного запаса; на низком окне уменьшать декоративные вертикальные отступы, заголовок и карточки вариантов. Масштаб просмотра не изменяет экспорт и общий scale документа.

Рабочие минимумы для обычной горизонтальной сцены при режиме «Вписать»:

| Viewport | Ширина рисунка не меньше |
| -------- | -----------------------: |
| 1440×900 |                   560 px |
| 1366×768 |                   420 px |
| 1280×720 |                   360 px |
| 390×844  |                   280 px |
| 320×740  |                   220 px |

Для квадратной и вертикальной сцены: не менее 90% максимально возможного вписывания в реальную область рисунка с предусмотренным небольшим запасом. При этом кнопки не перекрываются, страница не получает случайное горизонтальное переполнение, drag работает после resize/scroll/изменения масштаба.

Вместо вводящего в заблуждение «100%» исходного режима обозначить «Вписать». Если показывается процент, явно считать его относительным к вписыванию; не называть его масштабом физических пикселей.

### 7.2. Небольшие исправления

- Убрать квадратные угловые маркеры, которые выглядят как ручки индивидуального масштабирования. Простая рамка выделения остаётся.
- Поднять контраст доступных подпунктов и режимов. Для обычного мелкого текста — не ниже 4,5:1 без округления. Невыбранная, но доступная вкладка не является disabled-контролом. Основание: [W3C, Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
- Уточнить «Загрузить JSON-палитру», сохранить доступный образец.
- Убрать декоративную стрелку с неподвижной подписи, повторяющиеся служебные лозунги и избыточный заголовок, если они отнимают рабочее место. Сохранить статус записи, размер, число экземпляров и понятные ошибки.
- Поворот должен давать предсказуемую обратную связь. Если добавляем live-preview, он отделён от модели, отменяется при pointercancel/Escape и фиксируется одной Undo-командой; изменения слоёв/роли не попадают в чужую незавершённую операцию.

### 7.3. Кандидаты и смысловой ввод

Результат сборки привязан к снимку запроса: текст, режим, флаг фона, catalogVersion, revision сцены и токен запроса. Изменение любого параметра, влияющего на результат, отменяет задачу и делает старые варианты неприменимыми. Карточки можно оставить с ясной пометкой или очистить. Проверка актуальности обязательна и в обработчике применения, не только через disabled.

Словарь метафор не превращаем в новый AI-проект. Проверяем поддержанные темы и очевидный пропуск «Нет денег»; исправляем явные пропуски/ложные совпадения по границам слов на небольшом фиксированном корпусе. При неизвестном смысле остаётся честное уточнение. Нельзя добавлять ответ для каждого тестового заголовка отдельной скрытой веткой и выдавать это за общее понимание.

Файлы: `SceneView.tsx`, `Panels.tsx`, `App.tsx`, `styles.css`, точечно `semantics.ts`. Тесты: U01–U16, G01–G10, M01–M08.

## 9. Когда исправленная версия допускается к сдаче

- Нет открытого нарушения оригиналов/пропорций/цветовых правил и нет дефекта сохранности данных, основного редактирования или экспорта.
- Все обязательные сценарии проходят без retries, `.skip`, `.only` и ожидания «заведомого падения». Нестабильный обязательный тест считается незакрытой проблемой.
- A01–A06 закрыты ссылками на код, тест и реальное доказательство. Для A01 и A03 есть визуальное «до/после»; для A02 — фактические записи и возврат к проекту.
- При нормальной работе нет pageerror/unhandledrejection. При искусственном отказе есть управляемый результат, а не пустой экран или потеря сцены.

- Проверенный commit, fingerprint, dist, архивы, примеры, демо и публикация относятся к одной версии. После последнего изменения продукта связанные проверки выполняются снова.
- Если обязательный пункт не проверен или не пройден, итог — «к сдаче не готово». Новый балл выставляется после повторного аудита, заранее 8/10 или 10/10 не обещаем.
